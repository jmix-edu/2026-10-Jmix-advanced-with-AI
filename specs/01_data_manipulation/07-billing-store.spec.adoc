= 01_data_manipulation / 07 — Биллинг в отдельном хранилище
:toc:
:status: реализована

== Цель

Закрывать месяц по проекту: подтверждённое время за месяц фиксируется в
записях биллинга в отдельной базе, а сами списания становятся `CLOSED` и
больше не меняются. Биллинг живёт во втором хранилище `reports`, без ссылок
на сущности основного.

== В области

* Второе хранилище `reports`: PostgreSQL `ts_reports`, в тестах своя HSQLDB,
  свой changelog.
* Сущность `BillingRecord` в `reports`.
* Поле `TimeEntry.billingRecordId` в основном хранилище (см. «Согласованность»).
* Сервис `MonthClosingService` с операцией «Закрыть месяц».
* Действие «Закрыть месяц» на списке проектов.
* Экран списка `BillingRecord` только для чтения, пункт меню.
* Правка `TimeEntryRulesListener`: `APPROVED → CLOSED` только вместе с `billingRecordId`.
* Замена П4 из `05`: проект с `APPROVED`-списаниями закрыть нельзя.
* Сидер: `Legacy Support` закрывает прошлый месяц перед закрытием проекта.
* Ключи сообщений, интеграционный тест.

== Вне области

* Права: кто может закрывать месяц и видеть биллинг (M3).
* Read-replica и настройки продовых баз (M4).
* Деньги: ставки, суммы, счета. В записи только время.
* Отмена закрытия месяца: `CLOSED` по П3 необратим.
* Распределённые транзакции (XA/JTA): не вводим, см. «Согласованность».

== Хранилище `reports`

* Имя `reports`, JPA-хранилище. Создаётся в Studio (*Data Stores → New*).
  Studio генерирует класс конфигурации (datasource, EntityManagerFactory,
  `reportsTransactionManager`, Liquibase) и свойства в `application.properties`.
* `reports.datasource.url=jdbc:postgresql://localhost/ts_reports`, учётные
  данные — как их записала Studio. Базу `ts_reports` создаёт Studio при запуске.
* Changelog: `reports.liquibase.change-log` → корневой файл в
  `liquibase/reports-changelog/`, отдельный от основного.
* Тесты: в `application-test.properties` добавляю
  `reports.datasource.url=jdbc:hsqldb:file:.jmix/hsqldb/ts_reports_test`
  (`sa`, пустой пароль).

== BillingRecord

`@Store(name = "reports")`, таблица `TS_BILLING_RECORD`, UUID-id, `@Version`.

[cols="2,2,1,4",options="header"]
|===
| Атрибут | Тип | Обяз. | Смысл

| `projectId`   | `UUID`      | да | id проекта, без внешнего ключа и ссылки
| `projectName` | `String`    | да | имя проекта на момент закрытия
| `userId`      | `UUID`      | да | id пользователя, без внешнего ключа и ссылки
| `username`    | `String`    | да | логин на момент закрытия
| `month`       | `LocalDate` | да | первое число месяца; колонка `MONTH_`
| `spentTime`   | `SpentTime` | да | закрытое время пользователя по проекту за месяц
| `closedDate`  | `LocalDate` | да | дата последнего закрытия, сервер
|===

* Уникальный индекс `(PROJECT_ID, USER_ID, MONTH_)` в базе `reports`:
  одна запись на проект × пользователя × месяц.
* Имена проекта и пользователя хранятся снимком. Биллинг остаётся
  читаемым, даже если проект или пользователь потом архивированы или
  переименованы.
* `@InstanceName`: `projectName`, `username` и месяц.
* Traits и soft delete не нужны: записи меняет только сервис.
* Тип `SpentTime` хранится как `bigint` через тот же `SpentTimeConverter`.
  Риск: `autoApply` конвертера может не сработать во втором persistence
  unit. Тест это проверит, при сбое ставлю `@Convert` явно.

== Закрыть месяц

`MonthClosingService.closeMonth(UUID projectId, YearMonth month)` →
`List<BillingRecord>`, по одной записи на пользователя.

* Закрыть можно только прошедший месяц: `month` раньше текущего (дата
  сервера), иначе `IllegalArgumentException`. Текущий месяц ещё не
  кончился, люди продолжают списывать.
* Берутся списания проекта в `APPROVED` с датой внутри месяца. `NEW`,
  `REJECTED`, `CLOSED`, другие месяцы и другие проекты не трогаются.
* Нет `APPROVED`-списаний — ничего не меняется, существующие записи
  возвращаются как есть.
* Для каждого пользователя:
. Находится запись `(projectId, userId, month)` или создаётся новая.
. Его списания получают `status = CLOSED` и
  `billingRecordId = id записи`.
. Время записи пересчитывается как сумма всех списаний с этим
  `billingRecordId`, а не прибавляется к старому значению.
* Повторное закрытие того же месяца дублей не создаёт. Если после первого
  закрытия одобрили ещё списания за этот месяц, они прибавляются к той же
  записи. Без новых списаний повтор ничего не меняет.

== Согласованность двух хранилищ

Транзакции у хранилищ разные (`transactionManager` и
`reportsTransactionManager`), общей нет. Поэтому решаю порядок записи и
делаю операцию сходящейся при повторе.

.Порядок
. Основная транзакция (`@Transactional` на сервисе): списания переводятся в
  `CLOSED` и связываются с записями. Затем flush, чтобы правила `05` и
  оптимистическая блокировка сработали до записи в `reports`.
. В той же основной транзакции считается время записей. Свои
  незафиксированные изменения запрос видит.
. Записи `BillingRecord` сохраняются в `reports`, в своей транзакции,
  которая фиксируется сразу.
. Фиксируется основная транзакция.

.Что будет при сбое
[cols="2,3,3",options="header"]
|===
| Где упало | Состояние | Как чинится

| Шаги 1–2 (правило, конкурентная правка, ошибка БД)
| ничего не записано, основная транзакция откатилась
| исправить причину и повторить

| Шаг 3 (`reports` недоступна, нарушен уникальный индекс)
| `reports` не изменилась, основная транзакция откатилась
| повторить, когда `reports` доступна

| Шаг 4: фиксация основной после записи в `reports` (обрыв соединения)
| записи биллинга есть, списания остались `APPROVED`. Время в записи завышено или запись лишняя.
| повторить закрытие. Время пересчитается по фактически связанным
  списаниям, поэтому запись станет верной, дублей не будет.
|===

Окно расхождения — только между фиксациями шагов 3 и 4. Оно закрывается
повтором той же операции, а не ручной правкой. Поэтому время всегда
считается из основного хранилища по `billingRecordId`, а не накапливается.

Почему не наоборот (сначала основная, потом `reports`): при сбое
`reports` списания уже `CLOSED`, их нельзя ни изменить, ни удалить (П3),
и время пропадает из биллинга до повтора. Порядок «`reports` первым»
оставляет ошибку только в обратимой стороне.

Две параллельные операции на один проект и месяц: вторая падает на
оптимистической блокировке списаний (шаг 1). Если списаний не осталось,
она ничего не пишет. Уникальный индекс ловит гонку при создании записей.

Проверено по исходникам Jmix 3.0.2 (`JpaDataStore.beforeSaveTransactionCommit`):
`DataManager.save` внутри внешней транзакции сразу делает flush и
публикует `EntityChangedEvent`, поэтому правила срабатывают на шаге 1.
Сохранение в `reports` открывает свою транзакцию `reportsTransactionManager`
и фиксирует её по выходе из `save`.

== Поле TimeEntry.billingRecordId

* `UUID`, необязательное, без внешнего ключа: запись лежит в другой базе.
* Заполняется только сервисом закрытия, на форме и в списках не
  показывается.
* `TimeEntryRulesListener`:
** `APPROVED → CLOSED` требует `billingRecordId`. Закрыть одобренное время
   вручную, мимо биллинга, нельзя — иначе оно потеряется так же, как при
   закрытии проекта. `REJECTED → CLOSED` по-прежнему без него.
** `billingRecordId` меняется только вместе с переходом `APPROVED → CLOSED`;
   при создании, в `NEW`, в `REJECTED → CLOSED` и у `CLOSED` — отказ.

== Закрытие проекта (замена П4 из `05`)

Проект с `APPROVED`-списаниями закрыть нельзя: отказ с текстом правила,
проект остаётся открытым. Сначала закрываются их месяцы. Автоматическое
закрытие одобренных списаний при закрытии проекта убрано: оно обходило
биллинг. `NEW` и `REJECTED` закрытию проекта по-прежнему не мешают.

Сидер: списания `Legacy Support` перенесены в прошлый месяц; сидер
закрывает этот месяц через сервис, затем закрывает проект. На свежей
базе в биллинге сразу есть записи.

== UI

* *Список проектов*: кнопка «Close month», активна при выбранном проекте.
  Открывает диалог ввода с датой. По умолчанию прошлый месяц, берётся
  месяц выбранной даты. По «OK» вызывается сервис. Результат —
  уведомление «Closed N users, H:MM». Ошибка правила или неверный месяц —
  уведомление с текстом, без падения экрана.
* *Список `BillingRecord`*: генерирует Studio (только list, без detail),
  затем я убираю создание, правку и удаление. Остаются грид и фильтр.
  Столбцы: проект, пользователь, месяц, время (`ч:мм`), дата закрытия.
  Сортировка по месяцу (новые сверху), затем по проекту. Пункт меню после
  «Hours report».

== Тест

`MonthClosingServiceTest`: `@SpringBootTest`,
`@ExtendWith(AuthenticatedAsAdmin.class)`. Данные через `DataManager`.
Уборка через `JdbcTemplate` по основному `DataSource` и по
`reportsDataSource`. Месяц — в прошлом (2002 год), чтобы не пересекаться с
данными сидера.

* Закрытие создаёт по записи на пользователя с суммой его `APPROVED` за
  месяц. Время читается как `SpentTime`, конвертер работает в `reports`.
* Списания становятся `CLOSED` с `billingRecordId`. `NEW`, `REJECTED`,
  другой месяц и другой проект не тронуты.
* Повтор без новых списаний: число записей и время те же.
* Повтор после нового одобрения за тот же месяц: та же запись, время
  выросло, дублей нет.
* Сбой записи в `reports`: подменяю его тестовым слушателем на сохранение
  `BillingRecord`. Списания остаются `APPROVED`, записей нет.
* Сходимость после сбоя на шаге 4. Подкладываю в `reports` запись с
  неверным временем для того же ключа, как будто основная транзакция не
  зафиксировалась. Закрытие исправляет время, дубля нет.
* Текущий месяц — `IllegalArgumentException`, ничего не меняется.
* Правила (в `TimeEntryRulesTest`): `APPROVED → CLOSED` без
  `billingRecordId` — отказ; `billingRecordId` при создании, в `NEW`, у
  `APPROVED` без перехода, в `REJECTED → CLOSED` и у `CLOSED` — отказ;
  проект с `APPROVED` не закрывается; без них закрывается, `NEW` и
  `REJECTED` не трогает.
