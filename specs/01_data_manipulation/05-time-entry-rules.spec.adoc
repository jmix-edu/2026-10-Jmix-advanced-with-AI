= 01_data_manipulation / 05 — Правила учёта времени
:toc:
:status: черновик, ждёт ревью

== Цель

Сделать так, чтобы списание времени нельзя было сохранить в неверном
состоянии ни из формы, ни из сервиса, ни при импорте: проверки и переходы
статусов живут в слое данных, а не в UI.

== В области

* Проверки при создании, изменении и удалении `TimeEntry`.
* Жизненный цикл статуса `TimeEntry`.
* Автоматическое закрытие одобренных списаний при закрытии проекта.
* Тексты ошибок в `messages_en.properties`.
* Интеграционные тесты на все правила.

== Вне области

* Экраны согласования и удобные сообщения в UI (M2). Пока ошибка правила
  показывается стандартным диалогом Jmix с текстом из `messages_en.properties`.
* Права: кто может одобрять, отклонять, закрывать (M3). Правила ниже
  одинаковы для всех пользователей.
* Существующие данные: правила проверяются при сохранении, старые записи в
  `ts_live` не перепроверяются.
* Защита правила 24 часов от двух параллельных сохранений одного
  пользователя (см. «Известные ограничения»).

== Правила

=== П1. Закрытый проект, неактивная задача

Списание нельзя создать на задачу, у которой `status = INACTIVE` или проект
которой `status = CLOSED`. У существующего списания на такой задаче нельзя
менять поля (дата, время, задача, пользователь, описание); переходы статуса
из П3 разрешены — иначе списания `NEW` и `REJECTED` закрытого проекта
застрянут навсегда. Переназначить списание на такую задачу нельзя.

=== П2. Время

* `spentTime` больше нуля: `0:00` отклоняется.
* Сумма `spentTime` списаний одного пользователя за одну дату — не больше
  24 часов, с учётом сохраняемого списания. В сумму входят `NEW`,
  `APPROVED`, `CLOSED`; `REJECTED` не входит — отклонённое время не
  засчитано, его можно списать заново. Архивные (soft delete) не входят.

=== П3. Жизненный цикл статуса

[cols="2,3",options="header"]
|===
| Из | Разрешено в

| (создание) | только `NEW` — из формы, сервиса и импорта
| `NEW`      | `NEW` (правка), `APPROVED`, `REJECTED`
| `APPROVED` | `CLOSED`
| `REJECTED` | `CLOSED`
| `CLOSED`   | — ничего
|===

* Переход в `REJECTED` требует непустой `rejectionReason`.
* В `APPROVED` и `REJECTED` меняется только статус (и `rejectionReason` при
  переходе в `REJECTED`); остальные поля меняются только в `NEW`.
* `CLOSED`: никакие изменения и удаление не разрешены — ни напрямую, ни
  каскадом при удалении задачи или проекта (см. «Удаление»).

=== П4. Закрытие проекта

Когда `Project.status` меняется на `CLOSED`, все списания по задачам этого
проекта в статусе `APPROVED` переходят в `CLOSED` в той же транзакции. Если
закрытие одного из них не проходит, не закрывается и проект. Повторное
открытие проекта (`CLOSED` → `OPEN`) закрытые списания не трогает.
Списания `NEW` и `REJECTED` остаются как есть; их можно провести по П3 и
на закрытом проекте (П1).

=== П5. Удаление

Списание в `CLOSED` не удаляется никаким путём. Каскад архивации из спеки
`04-traits` (проект → задачи → списания) проходит через это правило, поэтому:

* задачу или проект, у которых есть закрытые списания, удалить нельзя — отказ
  с текстом правила, ничего не архивируется;
* закрытый проект остаётся в базе закрытым, его история не теряется;
* проект и задачу без закрытых списаний по-прежнему можно удалить (архивировать).

Это уточняет `04-traits`: архивация проекта целиком работает, пока у него нет
закрытых списаний.

== Как это устроено

* `TimeEntryRulesListener` (`com.company.timesheets.listener`) —
  `@EventListener` на `EntityChangedEvent<TimeEntry>`. Событие приходит до
  коммита, после записи в базу, в той же транзакции, при любом сохранении
  через `DataManager`; исключение откатывает всё сохранение.
** `CREATED` и `UPDATED`: загружает списание с задачей и проектом, старые
   значения берёт из `event.getChanges()`, проверяет П1–П3. Сумму за день
   считает запросом — сохраняемая запись уже в базе и входит в сумму.
** `DELETED`: старый статус из `getChanges()`, `CLOSED` — отказ (П5).
   Проверено при реализации: soft delete приходит именно как `DELETED`, со
   всеми атрибутами в `getChanges()`.
* `ProjectClosingListener` (там же) — `@EventListener` на
  `EntityChangedEvent<Project>`: если в `UPDATED` статус сменился на
  `CLOSED`, загружает одобренные списания проекта, ставит им `CLOSED` и
  сохраняет. Это сохранение проходит через `TimeEntryRulesListener`, и
  переход `APPROVED` → `CLOSED` на закрытом проекте должен быть разрешён П1.
* Загрузки внутри правил — через `UnconstrainedDataManager`: сумма за день и
  проверка проекта не должны зависеть от прав текущего пользователя (M3).
* Нарушение — `TimeEntryRuleException extends RuntimeException` с текстом из
  `messages_en.properties`, по ключу на правило.

Почему не `EntitySavingEvent`: в нём не подгружаются ссылки (`task.project`),
нет старых значений для проверки переходов, и он не приходит при удалении.

== Тесты

`TimeEntryRulesTest` — `@SpringBootTest`, `@ExtendWith(AuthenticatedAsAdmin.class)`,
сохранение через `DataManager`, без `@Transactional`.

* П1: создание на неактивной задаче и на задаче закрытого проекта — отказ;
  переназначение на такую задачу — отказ.
* П2: `0:00` — отказ; `20:00` + `4:00` за день — проходит; `20:00` + `4:01` —
  отказ; то же время в другой день и у другого пользователя — проходит;
  правка существующего списания не считает его дважды.
* П3: каждый разрешённый переход проходит, каждый запрещённый из таблицы — отказ;
  `REJECTED` без причины — отказ; изменение и удаление `CLOSED` — отказ;
  правка полей в `APPROVED` и `REJECTED` — отказ; создание сразу в
  `APPROVED` — отказ; переход статуса на закрытом проекте — проходит,
  правка полей там же — отказ.
* П5: удаление проекта и задачи с закрытым списанием — отказ, ничего не
  архивировано; без закрытых списаний — архивируются.
* П4: закрытие проекта переводит `APPROVED` в `CLOSED`, а `NEW`, `REJECTED` и
  списания других проектов не трогает. Откат всей транзакции проверяется в П5:
  после отказа в удалении проект и задача не архивированы. Отдельного теста на
  сбой при закрытии нет — переход `APPROVED` → `CLOSED` не может нарушить
  правила, сбой пришлось бы подделывать.

Уборка: данные теста удаляются в `@AfterEach` через `JdbcTemplate` (`DELETE`
по id в порядке внешних ключей). `DataManager` здесь не подходит: soft delete
оставил бы строки в файловой тестовой базе `.jmix/hsqldb`, а правило П3 не
даёт удалить `CLOSED`. Тестовые значения уникальны, класс проходит дважды
подряд.

== Известные ограничения

* Правило 24 часов проверяется в транзакции сохранения. Два одновременных
  сохранения одного пользователя за одну дату могут оба пройти. Блокировка —
  вне области; для табеля одного человека это маловероятно.

  бандла, не строка в коде.

  `@TransactionalEventListener`.

Проверяете вы (чек-лист Gate 3, после перезапуска приложения):

  на неактивную задачу — отказ с текстом правила, запись не сохраняется.
. Смена статуса `NEW` → `REJECTED` без причины — отказ; с причиной —
  проходит.

. Закрытие проекта переводит его одобренные списания в `CLOSED`
  (видно в списке списаний).
