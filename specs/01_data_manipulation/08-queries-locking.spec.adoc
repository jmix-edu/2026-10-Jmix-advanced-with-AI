= 01_data_manipulation / 08 — Запросы, fetch plan и блокировки
:toc:
:status: реализована

== Цель

Списки списаний и проектов фильтруются по частым сценариям без ручного ввода
дат, список списаний грузится без N+1, параллельная работа двух менеджеров
не теряет правок и не показывает стектрейс, а «Закрыть месяц» по одному
проекту не выполняется дважды одновременно.

== В области

* Список списаний: три сохранённые конфигурации `genericFilter`, даты в них
  считают JPQL-макросы Jmix.
* Список проектов: переключатель «Только мои проекты».
* Fetch plan списка списаний без N+1, проверка по SQL-логу.
* Оптимистичная блокировка при одновременной правке проекта: понятное
  сообщение второму менеджеру.
* Пессимистическая блокировка «Закрыть месяц» по проекту через add-on
  `jmix-pessimisticlock` (уже подключён в `build.gradle`).
* Ключи сообщений, тесты на макросы и блокировки.

== Вне области

* Права: кто видит чужие списания и кто закрывает месяц (M3). Фильтры здесь
  только сужают выборку и не ограничивают доступ.
* Кэш: query cache, кэш сущностей, их инвалидация.
* Кластер. Блокировки add-on хранятся в памяти одного экземпляра приложения.
  Для нескольких экземпляров нужен общий кэш (M4).
* Блокировка редактора проекта на время правки (пессимистическая). Для
  проекта остаётся только оптимистичная, см. «Почему не `@PessimisticLock` на
  `Project`».

== Что уже есть в Jmix 3.0.2

Проверено по исходникам и байткоду в Gradle-кэше:

* `@between(поле, now+N, now+M, единица)` разворачивается в
  `поле >= :p1 and поле < :p2`, где границы считает `TimeSource`. Единицы:
  `year`, `month`, `day`, `hour`, `minute`, `second`. *Единицы `week` нет.*
  Для `LocalDate` берётся часовой пояс сервера. `@today(поле)` тоже есть.
  `@dateBetween` принимает параметры, которые передаёт Java-код, поэтому не
  подходит.
* `:current_user_id` и вообще `:current_user_<атрибут>` подставляет
  `CurrentUserQueryParamValueProvider` (`jmix-security-data`) в любой
  запрос `DataManager`, в том числе в условия `jpqlFilter`. `JpqlQueryBuilder`
  считает такие параметры заданными, поэтому условие с ними не
  отбрасывается как условие без значения.
* `OptimisticLockExceptionHandler` (`jmix-flowui-data`, `@Order(150)`) уже
  перехватывает `jakarta.persistence.OptimisticLockException` и
  `org.eclipse.persistence.exceptions.OptimisticLockException` и показывает
  уведомление «The object has just been changed by another user…» без
  указания, кто именно изменил.
* При конфликте слияния (EclipseLink-5010) объекта нет ни в одном из двух
  исключений: `getEntity()` возвращает `null`, а `getObject()` падает с NPE,
  потому что нет query. Класс и id есть только в тексте:
  `The object [com…Project-<uuid> [detached]]`. Стандартный обработчик тоже
  берёт класс из текста.
* `LockManager.lock(name, id)` возвращает `null`, если блокировка взята.
  Если её уже держат, возвращает `LockInfo` с `getUsername()` и
  `getSince()`. Если для `name` нет `LockDescriptor`, возвращает
  `LockNotSupported`. Дескрипторы задают бины `LockDescriptorProvider`
  или `@PessimisticLock(timeoutSec)` на сущности.

== Фильтры списка списаний

В `time-entry-list-view.xml` у `genericFilter` появляются design-time
конфигурации. Каждая из них — `jpqlFilter` без параметра (скрытый, всегда
включён) или `propertyFilter`. Даты в Java не считаются.

[cols="2,5",options="header"]
|===
| Конфигурация | Условие

| Мои за 7 дней
| `{E}.user.id = :current_user_id and @between({E}.date, now-6, now+1, day)`.
  Это скользящие 7 дней, включая сегодня.

| За прошлый месяц
| `@between({E}.date, now-1, now, month)`: с 1-го числа прошлого месяца
  до 1-го числа текущего, не включая его. Все пользователи.

| По статусу
| `propertyFilter` по `status`, операция «равно», значение выбирают в
  фильтре.
|===

* Конфигурация по умолчанию не задана: список открывается без фильтра, как
  сейчас.
* Выбранная конфигурация попадает в URL через уже настроенный
  `urlQueryParameters`.
* Синтаксис `<configurations>` и `jpqlFilter` без параметра сверяю по
  Context7 до того, как писать XML.

== Только мои проекты

* В `project-list-view.xml` над гридом появляется чекбокс
  `onlyMyProjectsField`, по умолчанию выключен.
* Когда он включён, к запросу `projectsDl` добавляется условие
  `exists (select p from ts_ProjectParticipant p where p.project = {E} and p.user.id = :current_user_id)`.
  Когда выключен, условие снимается. В обоих случаях список перезагружается.
* Механизм: условие в `<query>` загрузчика,
  `:onlyMine = true and exists (... p.user.id = :current_user_id)`. Условия
  из XML загрузчика пропускаются, если какого-то их параметра нет, поэтому
  контроллер на чекбоксе `onlyMyProjectsField` только задаёт или убирает
  `onlyMine` и перезагружает список. Id пользователя в Java не берётся.
* Отдельный `jpqlFilter`-чекбокс не подошёл. `genericFilter` при смене
  конфигурации пересобирает условие загрузчика из *копии* исходного, и
  потом переключение чекбокса меняет уже не то условие, которое уходит в
  запрос.
* `dataLoadCoordinator` на этом экране ручной (`BeforeShow`), так и
  остаётся.
* Удалённые участники не учитываются: soft delete Jmix отсекает их в
  подзапросе сам.

== Fetch plan списка списаний

Сейчас fetch plan такой: `_base` плюс `user` (`_base`). Колонка `task`
выводит instance name задачи `[проект] имя`, у которого
`@DependsOnProperties({"name", "project"})`. Задача и её проект в план не
входят и догружаются лениво: до двух лишних `SELECT` на строку.

Новый план:

[source,xml]
----
<fetchPlan extends="_base">
    <property name="task" fetchPlan="_instance_name">
        <property name="project" fetchPlan="_instance_name"/>
    </property>
    <property name="user" fetchPlan="_instance_name"/>
</fetchPlan>
----

* Режим загрузки по умолчанию (`AUTO`) для many-to-one даёт `JOIN`.
  `fetchMode` явно не задаю, пока лог не покажет обратное.
* Новая колонка `task.project` («Project») рядом с `task`, для сортировки.
* Детальный экран списания не трогаю: у него свой план.

*Проверка по SQL-логу* (Gate 3, руками):
`logging.level.eclipselink.logging.sql=debug` на время проверки, потом
вернуть `info`. На одну страницу списка должно быть не больше одного
`SELECT` из `TS_TIME_ENTRY` с `JOIN` на `TS_TASK`, `TS_PROJECT`, `TS_USER`
и один `COUNT` для пагинации. Отдельных `SELECT ... FROM TS_TASK` или
`TS_PROJECT` по `ID` быть не должно, и их число не должно зависеть от
количества строк.

== Оптимистичная блокировка проекта

`Project`, `Task` и `ProjectParticipant` уже имеют `@Version`. Сценарий:
менеджеры A и B открыли один проект. A сохранил. B меняет поле и сохраняет.

* Сохранение B отклоняется, данные A не перезаписываются.
* B видит уведомление, а не стектрейс. Детальный экран B остаётся открытым:
  правки B не теряются, их можно перенести после переоткрытия.
* Если A и B правят разные задачи внутри одного проекта и сам проект не
  меняют, конфликта нет: версия проекта не растёт.
* Если A и B правят одну задачу, конфликт возникает на задаче, и сообщение
  то же.

Свой обработчик `OptimisticLockUiHandler` (`AbstractUiExceptionHandler`,
`@Order(100)`, раньше стандартного):

* находит класс и id устаревшего объекта: из исключения, если объект там
  есть, иначе из текста EclipseLink;
* загружает текущую версию и пишет: «Project "X" was changed by ivanov at
  … while you were editing it. Reopen it and apply your changes again».
  Данные берутся из `lastModifiedBy` и `lastModifiedDate` трейта аудита
  (спека 04);
* если объект не найден, удалён, у него нет этих полей или текст не
  разобрался, отдаёт исключение стандартному обработчику Jmix;
* сообщения только английские, как и весь бандл (`available-locales=en`).

== Блокировка периода при «Закрыть месяц»

* Имя блокировки `ts_MonthClosing`, id — `projectId`. Блокируется весь
  проект, а не пара «проект + месяц»: два закрытия разных месяцев одного
  проекта тоже идут по очереди.
* Дескриптор задаёт свой бин `MonthClosingLockDescriptorProvider`
  (`LockDescriptorProvider`) с таймаутом 600 секунд. Таймаут — страховка
  на случай зависшего потока. Обычно блокировку снимает `finally`.
* `MonthClosingService.closeMonth` становится нетранзакционным:
. `lockManager.lock("ts_MonthClosing", projectId)`;
. если вернулся `LockInfo`, выбрасывается `MonthClosingLockedException`
  с `username` и `since` держателя. Ничего не меняется;
. если вернулся `LockNotSupported`, это `IllegalStateException`, то есть
  ошибка конфигурации, а не сообщение пользователю;
. текущая логика из 07 выполняется в транзакции через `TransactionTemplate`
  основного хранилища;
. `unlock` в `finally`, уже после коммита основной транзакции, так что
  второе закрытие видит закрытые списания.
* Блокировку держит пользователь, а не сессия. Тот же пользователь из
  второй вкладки тоже получит отказ: `putIfAbsent` не смотрит на имя.
* Сидер вызывает `closeMonth` под `runWithSystem`, держатель там
  `system`. Это нормально.
* UI: `ProjectListView` ловит `MonthClosingLockedException` и показывает
  WARNING `closeMonth.locked`: «Месяц по проекту «%s» уже закрывает %s
  (с %s). Повторите позже».

=== Почему не `@PessimisticLock` на `Project`

Аннотация создаёт дескриптор с именем `ts_Project`.
`ViewPessimisticLockListener` блокирует сущность каждого детального экрана,
для которого есть дескриптор. Поэтому второй менеджер открывал бы проект
только на чтение, и сценарий с оптимистичной блокировкой пропал бы. Своё
имя `ts_MonthClosing` экраны не затрагивает.

== Тесты

`TimeEntryFiltersUiTest` (UI-интеграционный, по образцу `UserUiTest`):

* открывает `TimeEntryListView`, выбирает конфигурацию в `genericFilter` и
  проверяет содержимое `timeEntriesDc`. Тест идёт через настоящий XML и не
  повторяет JPQL в Java;
* данные относительно `LocalDate.now()`: сегодня, сегодня−6 и сегодня−7
  для admin; сегодня для другого пользователя; первый и последний день
  прошлого месяца; первый день текущего месяца;
* «Мои за 7 дней» — только записи admin за сегодня и сегодня−6;
* «За прошлый месяц» — обе границы прошлого месяца, без 1-го числа
  текущего, для всех пользователей;
* «По статусу» с `APPROVED` — только одобренные.

`MonthClosingServiceTest`, новые случаи:

* *второе закрытие ждёт первое.* Поток 1 закрывает месяц и останавливается
  на `EntitySavingEvent<BillingRecord>`: тестовый слушатель ждёт
  `CountDownLatch`. Поток 2 закрывает тот же проект и получает
  `MonthClosingLockedException` с `username = admin`. После отпускания
  поток 1 завершается, записей биллинга нет дублей;
* *другой проект не блокируется:* пока поток 1 держит проект A, закрытие
  проекта B проходит;
* *блокировка снимается после ошибки:* закрытие падает (уже есть
  `FailingReportsStore`, теперь `ReportsStoreHook`), следующее закрытие
  того же проекта проходит;
* *проект не закрывается во время закрытия месяца* (вопрос 4): пока поток 1
  держит блокировку, смена статуса проекта на `CLOSED` получает
  `TimeEntryRuleException`, проект остаётся `OPEN`.

Тестовые HSQLDB переведены в `hsqldb.tx=mvcc` (`application-test.properties`).
В режиме по умолчанию (`LOCKS`) открытая транзакция первого потока
блокирует таблицу `TS_TIME_ENTRY` целиком, и закрытие другого проекта
зависло бы. MVCC ближе к поведению PostgreSQL.

`ProjectOptimisticLockTest`:

* две копии одного проекта, сохраняется первая, затем вторая:
  `OptimisticLockException`, в базе значение первой;
* `OptimisticLockUiHandler.describe(...)` на этом исключении возвращает
  текст с именем проекта и `admin`.

«Только мои проекты» и fetch plan автотестами не покрываются: это Gate 3.

== Решения по ревью

. «Мои за эту неделю» — скользящие 7 дней, включая сегодня. Конфигурация
  называется «My last 7 days» (`filter.myLastWeek`).
. Конфликт версий — свой обработчик с «кто и когда».
. Блокируется весь проект.
. Закрытие проекта отклоняется, пока по нему идёт «Закрыть месяц»:
  `ProjectClosingListener` смотрит `getLockInfo` и выдаёт
  `project.monthClosingInProgress` с именем держателя.

== Критерии приёмки

. На списке списаний есть три конфигурации фильтра. Их условия написаны
  на JPQL с `@between` и `:current_user_id`, в Java даты не считаются.
. «Мои за 7 дней» показывает только списания текущего пользователя за
  последние 7 дней, включая сегодня. «За прошлый месяц» — все списания с 1-го по последнее
  число прошлого месяца. «По статусу» — только выбранный статус.
. Чекбокс «Только мои проекты» оставляет проекты, где текущий пользователь
  — неудалённый участник. Выключение возвращает все проекты.
. Список списаний показывает задачу, проект и пользователя. В SQL-логе
  на страницу один `SELECT` с `JOIN` и один `COUNT`, без запросов на каждую
  строку.
. Второй из двух менеджеров, сохраняющих один проект, получает уведомление
  с именем того, кто сохранил раньше, и временем, а не стектрейс. Данные первого не перезаписаны.
. Пока по проекту идёт «Закрыть месяц», второе закрытие того же проекта не
  начинается и сообщает имя держателя и время. Закрытие другого проекта
  проходит. После любой ошибки блокировка снята.
. `gradle clean test` зелёный, включая новые тесты.
