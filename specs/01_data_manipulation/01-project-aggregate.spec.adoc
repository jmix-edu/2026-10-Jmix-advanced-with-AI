== Модель

`ts_` / `TS_`, генерируемый `UUID`, `@Version`, аксессоры вручную. Длинный текст —

=== Project — новые атрибуты

[cols="2,2,4",options="header"]
|===
| Атрибут | Тип | Ограничения

| `description` | `String`        | `@Lob`, длинный текст
| `status`      | `ProjectStatus` | колонка `STATUS`, `nullable = false`, `@NotNull`; по умолчанию `OPEN` — инициализатором поля

=== Task — новые атрибуты

[cols="2,2,4",options="header"]
|===
| Атрибут | Тип | Ограничения

| `description` | `String`     | `@Lob`, длинный текст
| `status`      | `TaskStatus` | колонка `STATUS`, `nullable = false`, `@NotNull`; по умолчанию `ACTIVE` — инициализатором поля
| `taskType`    | `TaskType`   | `@ManyToOne(fetch = LAZY)`, `@JoinColumn(name = "TASK_TYPE_ID")`, необязательная; индекс в `@Table`

* `Task.project` получает `@OnDeleteInverse(DeletePolicy.CASCADE)`. Остальное в
  этой ссылке не меняется: она уже обязательная и `LAZY` и служит обратной
  ссылкой композиции.
* Имя экземпляра — метод с `@InstanceName` и `@DependsOnProperties({"name", "project"})`:
  `[<project.name>] <name>`. Без проекта — просто `<name>`.
* `@InstanceName` снимается с поля `name`.

=== Каскадное удаление задач

Каскад описан с двух сторон:

* `Project.tasks` — `@OnDelete(DeletePolicy.CASCADE)`;
* `Task.project` — `@OnDeleteInverse(DeletePolicy.CASCADE)`.

По документации Jmix (Data Model → Entities → Deletion Policy):

* для сущности с soft delete оба правила выполняет фреймворк во время работы;
* для сущности без soft delete `@OnDeleteInverse` с `CASCADE` Studio переводит
  в внешний ключ с `ON DELETE CASCADE` при генерации changelog.

У `Project` сейчас есть soft delete, поэтому удаление проекта — это `UPDATE`, а
не `DELETE`, и каскад выполняет Jmix. Задачи (soft delete у них нет) удаляются
физически в той же транзакции. Каскад в базе при этом не срабатывает, потому что
строка проекта не удаляется. Будет ли Studio генерировать `ON DELETE CASCADE`
для ссылки на сущность с soft delete, проверяю при сверке changelog. Если
soft delete с `Project` когда-нибудь уберут, каскад в БД из `@OnDeleteInverse`
останется в силе.

== Очистка тестовых данных

Перед генерацией changelog и до перезапуска приложения Claude удаляет в базе
`ts_live` все строки из `TS_TASK`, затем из `TS_PROJECT`. Удаление физическое
(SQL `DELETE`), в обход soft delete. Другие таблицы не трогаются. Перед
удалением Claude показывает число строк в обеих таблицах.

Зачем: у `TS_PROJECT` появляется обязательный `CLIENT_ID`, и на существующих
строках changelog с `NOT NULL` упадёт.

== Критерии приёмки

Проверяет Claude (сверка с changelog, Gate 1 и 2):

. Перед миграцией `TS_TASK` и `TS_PROJECT` в `ts_live` пусты, остальные
  таблицы не изменены.
